# 三視圖複刻工作流（triview——把雕塑問題轉成量測問題）組合範例
> 適用範圍：有真正交三視圖／工程圖（L1 等級，見下方「啟動判準」）可依據的真實物件複刻——
> 對稱、有主軸、輪廓可放樣的品類（手機、家電、車、船、瓶罐、家具）。不適用重複件/陣列/
> 規則格狀量體（建築立面、街道、桌椅，走既有 `building_lib` 等流程）、原創設計（走風格卡+
> 比例系統）、有機造型/布料/植栽/地形（走 `nature_lib`/`parametric_surface`）。
> 涵蓋工具：`triview_lib.py`（影像端）、`triview_build.py`（幾何端·外殼）、`triview_loft.py`
> （幾何端·放樣）、`blueprint_lib.py`（標註平面圖）、`component_lib.py` + `component_measure.py`
> （元件表×三視圖對賬）
> 最後更新：2026-09-13（從 SKILL.md §16.9 抽出獨立成檔，內容未刪減——原節 430 行、佔
> SKILL.md 當時篇幅超過四分之一，是這一輪 SKILL.md 瘦身的最大單一抽出對象；SKILL.md 保留
> 精簡版路由指向本檔）

## 前置知識

必查 §11 Stage A（設計簡報流程）與 §11 Stage C（視覺評審流程）——本工作流**不取代**它們，
是它們的量測層，見下方「本工作流不取代既有 Stage A」一節。判斷「這次任務要不要用三視圖」
一律先看「啟動判準」一節，不要憑直覺決定。

## 核心洞見

**AI 建模最致命的三個弱點是「盲寫座標、看不到中途、對連續曲面沒手感」**。三視圖把**發明**
這個環節整個抽掉——圖紙已經把比例與輪廓回答完，剩下的全是「校準 → 萃取 → 放樣 → 驗證」，
正好落在 AI 的強項上。這跟 `even_bays()`「目標間距反推格數」是同一套哲學：不要猜，去量。

**六階段與分工**：0 校準對位 → 1 輪廓萃取 → 2 斷面合成（視覺外殼）→ 3 站點斷面放樣 → 4 拓撲
正規化（quadriflow）→ 6 閉環驗證（回渲剪影 ↔ 來源輪廓 IoU／到邊界 Hausdorff）——由
`triview_lib`／`triview_build`／`triview_loft` 承擔。**階段 5（A 級曲面與細節）不屬本流程**：
曲面倒角／過渡／細分交給 `shape_lib`，材質與細節件交給 `mat_lib`／`detail_lib`。

**人類檢查介面（選用）**：`blueprint_lib` 產生帶 `A-n`／`Fn` 編號的標註平面圖，讓使用者用
「`A-3` 位置不對」「`F7` 這條線不對」回報——出圖時機、編號規則與已知限制見「標註平面圖」
一節。它不產生幾何、不取代任何階段。

## 檔案分工（兩端刻意解耦，中間只靠 JSON 溝通）

| 端 | 檔案 | 執行環境 | 產物 |
|---|---|---|---|
| 影像端 | `assets/triview_lib.py` | 純 Python 3 + numpy + Pillow（工作區 venv，**不經 bpy**） | `triview_calib.json`（純資料，mm） |
| 幾何端 | `assets/triview_build.py` | Blender headless | `.blend`、回渲 PNG、`triview_build_report.json` |
| 幾何端（放樣） | `assets/triview_loft.py` | Blender headless（重用 `triview_build` 的 mesh/量測工具層） | `.blend`、回渲 PNG、`triview_loft_report.json` |

分開的理由：Blender 內建 Python 沒有 Pillow，混在一起會讓影像端只能在 Blender 裡跑；分開後
任一端都能獨立重跑與除錯。`triview_lib` 的 Pillow 是延遲載入，所以 Blender 端仍可 import 它
只為呼叫 `load_calib()`/`save_calib()`。

## 強制規則

1. **輸入等級＝下方「啟動判準」步驟二的 L1**（真正交視角＋標註數字）；非 L1 不進本節。L1 的
   取得管道優先找官方尺寸圖（Apple 的 Accessory Design Guidelines 提供數十款產品的
   dimensional drawings，每頁含正/側/背視圖與完整標註）；取得後驗 magic bytes（PDF 檔頭
   `25 50 44 46`），不要只信 HTTP 200。
2. **ROI 選擇是設定步驟，不是自動化保證**。`find_panels`（留白溝切分）在密集工程圖上會把
   尺寸線群誤判成面板；可靠路線是 `find_body_candidates`（降採樣連通塊 + 面積/長寬比）給
   候選 → 看疊圖確認 → ROI 寫進 `config.py` 成為具名常數。把 ROI 固定下來，重跑才可重現。
3. **降採樣只用於定位，輪廓一律在全解析度 ROI 上萃取**。低解析度直接輸出輪廓會損失精度。
4. **至少兩張正交視圖才能成形**（兩視圖視覺外殼＝正視圖沿深度拉伸 ∩ 側視圖沿寬度拉伸）。
   這是人類面對「只有兩張正交視圖」時的標準做法，比逐點猜座標可靠得多。
5. **有標註數字時以標註為準**：外殼量測會受圖面線寬影響（墨線中心 vs 輪廓外緣），
   `build_visual_hull(depth_override_mm=, width_override_mm=)` 用標註值覆寫最終尺寸。
6. **視覺外殼的天花板要主動聲明，不要假裝它全能**：它**抓不到輪廓內部的凹凸**（輪拱、
   腋下開孔會被填平），也**會把非輪廓特徵放大**（背面相機凸台的真實長度會變成全寬度）。
   這些要另外用標註尺寸補件，或加量測視角——不要硬套外殼後假裝做完了。
7. **對照圖能看出來的差異，一律修正完再交付（不得只修一半）**：這是**驗收標準**，不是單輪
   的施工範圍——施工照「迭代狀態管理」規則 4 拆成多輪、每輪一個元件群（一輪只動一群，才能
   保證上一輪對的地方不被打掉）。一旦手上有了參考圖，判準就從「跑通驗證」升級成「跟圖對得
   上」。具體要求：
   - **逐項核實到底，不是抽查**：外框尺寸、圓角、邊距、每個子元件的位置/大小/相對關係，
     圖面看得到的全部要對。只改了「使用者點名的那幾項」不算完成。
   - **憑印象加上去的東西要移除**：圖上沒有的元件（多墊的板、多畫的環），
     即使外觀看起來合理也要砍掉——它們會把正確元件的相對關係一起帶歪。
   - **量測與標註衝突時不自行挑值**（例：底板角半徑量測 9.10mm vs 圖面標註 R14.00）——
     記進 `params[].conflicts`、寫下裁決依據，未裁決即擋下（「迭代狀態管理」規則 3）。
   - **整體比例也要跟圖對**：元件級尺寸全對，機位造成的透視壓縮仍可能讓成品「看起來
     偏瘦/偏扁」。交付前用投影寬高比對比圖面輪廓寬高比（如後視圖 78/163.4 = 0.477），
     差距明顯就是方位角要調，不是幾何錯。
   - **材質的視覺讀感同樣算「看得出來」**：一片高反射玻璃在棚拍下把主光原樣鏡射成硬邊
     亮塊、近黑材質讓該讀成平面的環讀成立體框——這些都屬於「圖上一眼可見不符」。
   - **量測值與圖面標註衝突時，先懷疑量測抓錯了零件外框，不要先判標註有誤**：一次錯誤的
     掃描會把正確的標註逼走，而且之後所有「自洽檢查」都在錯誤前提上照樣通過（實測：底板
     寬度被量成 69mm，於是推出「採 R14 會使板寬超過機身」而丟棄圖面標註 R14、改採推論值
     9.10——自洽是真的，三個數卻同源於同一次錯掃）。**量測要鎖在圖面已標註的兩個特徵之間
     （例如兩顆鏡頭中心距），不要靠外框輪廓推比例尺**；下結論前先找第二個獨立來源
     （另一張細節圖、官方文案、實機照）交叉驗證。

## 實測陷阱（Blender 5.1 工具鏈；違反任一 = 靜默出錯）

| # | 陷阱 | 後果 | 正確做法 |
|---|---|---|---|
| 1 | 布林用 `EXACT` solver | 尺寸看起來正確，**體積只剩 40%**、47 條非流形邊，側視圖渲成細線 | 一律 `MANIFOLD`（5.1 新增）；列舉只剩 `FLOAT`/`EXACT`/`MANIFOLD`，舊版 `FAST` 已移除會拋 TypeError |
| 2 | 平面輪廓先三角化再 `SOLIDIFY` | 沿加權法向位移把板子沿非拉伸軸撐出尖刺（163.16 → 175.98mm） | 用 n-gon 直接加厚；布林求解器自己會三角化 |
| 3 | 兩片拉伸板在共同軸上共面 | 布林塌成細條 | `build_visual_hull` 預設以 `extend_axis_scale` 等比外擴 0.5mm；**必須等比縮放，移動極值端點會產生退化多邊形而靜默失敗** |
| 4 | 輪廓纏繞順序錯誤（角落圓弧串成蝴蝶結） | 布林體積塌到 0.8% | `normalize_contour` 正規化；`polygon_sanity` 守衛（面積 ÷ 包圍盒 ≥ 0.25）在入口 raise |
| 5 | 正交相機盯著世界原點 | 主體被裁掉一半（163mm 只拍到 102mm） | 取景中心 = 主體實際世界中心（`world_center()`） |
| 6 | `fill_holes` 開在整頁上 | 圖框圍住的整張圖變成一個實心塊，所有候選被吃掉 | 補洞只在已裁好的 ROI 內做（`use_fill=False` 為全頁預設） |
| 7 | 回渲 PNG 比對時又套一次 `to_mm_contour()` 的 y 翻正 | 量到的 z 上下顛倒 | 回渲影像列序是 bottom-up（`bpy.data.images.pixels` 第 0 列＝畫面底部）：`mm_z = (row − 最底列) / ppm`，不可再翻正 |
| 8 | 閉環用「點對頂點」Hausdorff／直接以 1px 柵格化算 IoU | 量到 80mm 假距離；分數被量化誤差主導 | 一律用 `boundary_hausdorff_mm()`（點對線段）；IoU 先等比放大 `raster_scale`(=4) 再柵格化 |

**驗證不可省**：`assert_spec` 對標註尺寸做硬性斷言（超差印 `SPEC_ASSERT_FAIL`，容差由
`TRIVIEW_TOL_PCT` 控制，預設 2.0），並把回渲 PNG 用 `read_image_native`（或你的 agent 平台上等價的視覺輸入工具）看一眼——
正視圖應是完整主體剪影而不是細條。**尺寸錯跟方向錯同罪**，1-2% 的誤差在圖上根本看不出來。

**適用邊界與實測**：有官方正交尺寸圖（如 Apple）走本流程、各項誤差 ≤1.59%（iPhone 17 Pro Max：
正視圖寬 77.970mm −0.04%、高 163.159mm −0.15%、側視圖厚 8.651mm −1.14%、回渲正視 −0.06%、
回渲側視 −1.59%、跨視圖高度比 0.99963；成形幾何 708 頂點 / 非流形邊 0）；官方不發布正交圖的
品類走規格驅動（Famicom ≤1.18%、SU7 ≤0.66%，軸距 3000 精準）。**透視照可作尺度推估，但精度
有限**：同一個主體不同角度的照片量出來的長高比可以差一大截（SU7 側面照量得 2.28~3.08 vs 官方
3.46，誤差 12~34%）——所以推估值必須標明是估計，一有圖面標註或官方規格就讓位。

規格驅動路線的重點不是放棄量測，而是**把權威數字直接寫成 assertions 的硬點**
（`assert_spec` 那一套照用），並在交付時聲明哪些是官方數字、哪些是造型判讀。
剖面控制點優先用 `shape_lib.profile_loft()`（回傳 `(obj, section_fn)`），
**注意它不回算面法向量，呼叫端必須自己 `recalc_face_normals`**，否則整個量體渲成黑面。

**構圖入鏡同樣要量化**：`auto_frame_and_light(ortho_margin=...)` 之外，直接讀
`SCENE_STATE.auto_geometry_audit.framing.coverage` 確認主體完整入鏡——實測 Famicom
第一版因留白不足把兩側控制器切出畫面，是這個欄位攔下來的。

## 啟動判準（使用門檻的唯一來源）

**本節是「要不要用參考圖、誰去找、用哪一種、能證到什麼程度、找不到怎麼辦」的唯一判準，且
只在兩個時機被引用**：規劃初期（SKILL.md §11 Stage A，還沒動工、決定要不要找圖）與校正期
（SKILL.md §11 Stage C，已建模但被使用者指出大量元件位置/大小/方向錯誤）。其餘章節不重述、
也不指向本節。

**一句話總則**：有真實對應物 → 圖優先於猜；原創設計 → 風格／比例系統優先於圖；圖的等級決定
它能證什麼，不能跨級使用——**高階圖缺位時低階圖仍然可用，只是精度下降、必須標明是估計**——
沒有正交圖時，普通照片仍能讀對構型與方向，並提供比例／角度的粗略推估；**有推估永遠優於
憑空亂畫**（完全沒有圖就開工，等於整套尺寸全靠猜，比拿照片推估更差）。

**步驟一 · 任務性質（決定「要不要去找圖」）**

| 性質 | 判別 | 動作 |
|---|---|---|
| **A 複刻真實存在的物件** | 有名字、有官方來源，或使用者明說「照這個做」 | **強制找圖**：文字規格（§11 Stage A item 2）＋正交圖（存在時）＋照片推估（無正交圖時 1–3 張）＋色調判讀 |
| **B 原創設計** | 沒有可對應的真實型號，或使用者說「自由發揮」 | **不找尺度圖、不進 triview**；走風格卡（§17）＋比例系統（§15）＋`proportions_lib`。參考圖只能當**造型語彙**看——原創設計沒有可對應的真實尺寸，比例一律走 §15 比例系統與 §17 風格卡。**但元件表與拆解深度照樣要過**——原創設計仍必須產出 `components.json` 並通過 `component_lib depth`（不需 calib／三視圖，預設 6 級，§11 Stage A item 3）；「不進 triview」不等於「不受任何檢查」，這正是它過去唯一一條寫成 MUST 卻沒有閘門的規則 |
| **C 使用者主動提供圖** | 對話裡有附檔/連結，不分等級 | 先讀（§11 Stage A item 4），再依步驟二判它能幹嘛 |
| **D 既有場景加件／改件** | 不涉及主體複刻（「在那張桌上加個杯子」） | **不啟動** triview 流程 |

**步驟二 · 素材等級（決定「這張圖能證什麼」）**

| 等級 | 素材 | 可證範圍 | 禁止 |
|---|---|---|---|
| **L1** | 正交尺寸圖：真正交視圖＋標註數字、官方工程圖 | triview 全流程（階段 0–4 校準／輪廓／成形／拓樸 ＋ 階段 6 閉環驗證）；標註尺寸寫成硬性斷言（`assert_spec`）。階段 5 曲面與細節由既有 lib 接手，不屬本流程 | — |
| **L2** | 透視照：產品照／宣傳照／評測照 | 色調、材質、裝配關係、**構型與方向語義**（標線／機構的走向、字體朝向、子元件相對位置、大區塊結構）、缺件核對（§13.12）、**比例的粗略推估** | 推估值一律標 `estimated`，**不得與圖面標註／官方規格同級引用**；同主體有後者時一律以它覆蓋 |
| **L3** | 3D 參考檔（`.obj`/`.fbx`/`.gltf`/`.stl`…） | 只量整體比例／階層（§19.4，量完即丟） | **幾何不得進最終輸出** |
| **L4** | 只有官方規格數字 | 規格驅動建模：數字寫成 `assert_spec` 硬點，造型用 `shape_lib.profile_loft()` 剖面控制點描述 | **不假裝做過 triview** |

**L1 缺位時 L2 的角色（找不到正交圖就靠這段）**：正交圖找不到、或找到但品質不達標時，不代表
只能憑規格想像——挑 **1–3 張**角度盡量分散到接近正／側／頂的照片（三向都有最好，只有一兩向
也可），逐張回答「這張能確認什麼」，把構型、方向與比例推估的結論寫進 Stage A 元件表，不要
只留在對話裡。這類判讀**不受透視畸變影響**，因為讀的是「有沒有、朝哪邊、誰在誰旁邊、大塊
怎麼分」，不是長度：標線與跑道的走向、舷號／機身編號的字向、上層結構與相鄰艙面的相對位置、
大面積結構分區，都可靠照片一次修正——構件多、造型沒有把握的主體（艦艇甲板、大型載具、複雜
機構外殼）用這條最划算。**尺寸／角度／比例同樣可以推估**：透視照沒有比例尺、鏡頭焦距未知，
推出來的值只能當建模起點與 sanity check；一旦有圖面標註、官方規格或 L1 量測值，一律以那些
覆蓋——不是「不能推」，是「推了要標明精度、並在有權威值時讓位」。

**步驟三 · 找圖責任（誰去找、找幾輪、找不到／讀不出來怎麼辦）**

- **責任歸屬**：**A 類而使用者沒給 → AI 負責主動搜**（份內工作，不是被動等補圖）；C 類
  （使用者已給）直接用、不重複找；B／D 類不找。
- **搜尋上限**：AI 主動搜 **2–3 輪就停**——找到 L1 走 triview；只有 L2 就算「找到了」，先抓
  **1–3 張**（角度盡量分散到正／側／頂）做完構型與比例推估的判讀，再走規格驅動；兩者都沒有
  才進下一條。
- **完全找不到 → 不卡住**：照 §11 Stage A item 2 的文字規格建模，在簡報明講「本次未取得
  參考圖，屬造型判讀」，把缺口打包進反問輪讓使用者決定要不要補圖。
- **圖已在手但讀不出來**（工具被拒／模型無視覺）→ `read_image_native`（或你的 agent 平台上等價的視覺輸入工具）一次、`describe_image`
  一次，**兩次不成就停**，改照文字規格繼續，缺口同樣打包進反問輪。
- **一律不得無限糾結**：搜圖與讀圖都不是「不看就不能動工」的硬性關卡；禁止為了找一張「能讀
  的圖」反覆抓取／裁切／重試第三、第四張候選圖，也禁止自行發明讀圖替代方案（尤其把圖片轉成
  ASCII／像素文字自己「量化判讀」）。找不到就是找不到，改走文字規格並把缺口攤給使用者。

**步驟四 · 建模對象分流（有沒有 L1 圖都先過這關，決定成形路線）**

| 對象類型 | 走哪條 |
|---|---|
| 重複件、正交量體、陣列、規則格狀（建築立面、街道、桌椅） | **既有流程**（`building_lib` 等），三視圖不需要 |
| 對稱、有主軸、輪廓可放樣（手機、家電、車、船、瓶罐、家具） | 有 L1 → 本流程；無 L1 → 規格驅動，並用 L2 照片補構型、方向與比例推估（步驟二） |
| 有機造型、布料、植栽、地形 | 既有流程（`nature_lib`／`parametric_surface`） |

**順序**：一（要不要找）→ 二（能證什麼）→ 三（誰去找、找不到怎麼辦）→ 四（成形路線）。
門檻只在這一節；其他章節要改判準時回來改這裡，不得就地新增第二份。

## 本工作流**不取代**既有 Stage A（最高優先約束）

三視圖解決的只有一件事：**把「這個物件的空間關係、位置、大小」從猜測變成量測**。
它不解決「這是什麼、由哪些零件組成、該給什麼材質」——那仍然是 §11 Stage A 的職責，
**而且必須保留，一點都不能少**：

1. **資料蒐集**：查真實規格、官方數字、權威來源，寫進簡報當建模依據。
2. **元件拆解**：層級式元件表（LEVEL 1→6）、六面清單／空間必備元素清單、成對組件、
   材質 factory、邊緣處理半徑、內嵌留白、文字裝飾評估、磨損評估。
3. **反問確認**：設計簡報呈現給使用者、等一次確認才動工。
4. **既有 lib 體系**：`mat_lib`／`detail_lib`／`shape_lib`／`building_lib`／
   `build_template`（曝光配方、LUMA 守衛、語義斷言、構圖斷言）。

正確的接法是**兩者相乘**，不是二選一：

```
Stage A 資料蒐集 + 元件拆解        ← 永遠先做：決定「這是什麼、由哪些零件組成、什麼材質」
        │
        ├─ 有完美正交三視圖 → 六階段提供每個零件的確切尺寸/位置/輪廓
        │                     元件表照樣逐項存在，只是尺寸欄位由量測值填入
        │                     而不是由 AI 憑印象估
        └─ 無正交三視圖   → 規格驅動建模：官方數字當硬性斷言，
                              造型用 `shape_lib.profile_loft()` 的剖面控制點描述
```

**元件表與三視圖的對賬，就是這條「相乘」關係的落地**（見「元件表 × 三視圖 對賬」一節）：
CP1 在動工前拿元件表去問三視圖「這個零件在圖上查得到嗎、參數有標註嗎、有沒有哪個視圖完全
沒被元件覆蓋」，CP2 在框架建好後拿三視圖量出來的數字回頭校正元件表——兩者都以元件表為共同
語言，所以 **Stage A 拆到多細，直接決定這條迴圈能檢查到多細**。

**這條迴圈要能連續跑好幾輪，還需要第三塊——狀態管理**（見「迭代狀態管理」一節）：量測解決
「形狀對不對」、對賬解決「模型跟表對不對」，但如果每輪都重新動整個場景，上一輪已經驗證過的
正確區塊會被順手打掉。`locked`／`revision`／`diff --scope` 三件事就是讓「改一處、不影響
其他處」從願望變成 exit code 的機制——**三塊缺一，複刻就會在「改 A 壞 B」之間來回震盪**。

沒有 Stage A，量出來的輪廓不知道對應到哪個零件、該給什麼材質、該不該挖洞；
沒有三視圖，Stage A 的元件表只能填估計值。**斷面圓角就是最清楚的例子**：
那是第三個平面的性質、量測不到（見 §0.5 `resolve_corner_radius_mm`），所以它的
優先序是「圖面標註 > 對該品類的知識 > 估計」——量測給座標、知識給工藝。

## 兩條成形路線怎麼選（外殼 vs 放樣）

| | 視覺外殼 `triview_build` | 站點放樣 `triview_loft` |
|---|---|---|
| 手法 | 兩輪廓各拉一片厚板做布林交集 | 沿主軸逐站掃描跨度→斷面→橋接 |
| 擅長 | 兩視圖就足夠成形、輪廓內側無凹陷的物件 | 需沿主軸逐站修形、需要乾淨四邊拓撲的物件 |
| 拓撲 | 布林碎面（三角為主），需 Stage 4 重拓 | 天生全四邊、零非流形 |
| 已知代價 | 填平輪廓內側凹陷 | 斷面取外包絡，凹陷同樣被填平但**會回報 `max_span_runs`** |

兩者共用同一套「回渲 → mm 量測 → 閉環 IoU」驗證，報告格式一致，可並排比較選用。

**Stage 3 的已知代價（誠實記錄）**：站點跨度取 min..max 外包絡，凹陷處會被填平——
`scan_spans` 回報 `n_runs`、`build_station_loft` 回報 `max_span_runs`，**凹陷是真實
存在的話數值上看得到，不會靜默消失**（iPhone 實測 `max_span_runs=2`，正是輪廓側邊
按鍵缺口）。真正的解法是「加量測視角」或分段建模，不是硬套。

**Stage 6 閉環**：回渲 → mm 量測 → IoU／Hausdorff。兩個實測陷阱（回渲列序 bottom-up、
Hausdorff 用點對線段）見上方陷阱表 #7／#8，不在此重述。

**與其他章節的關係**：
- 這是 §19.4「3D 參考檔研究」的**升級版**——參考檔研究只拿來「量」然後丟掉，三視圖是直接
  把 2D 正交投影當施工圖，量測與建模共用同一份真相源。
- 完整操作手冊、實測數據與重跑指令：`.capybala/notes/triview-workflow.md`。

## 標註平面圖（blueprint_lib——人可以指著它說話的那張圖）

**定位**：triview 能「量」輪廓、能「建」幾何，但中間缺一個**人類可指認的介面**——Stage A 的
元件表是純文字，看不出哪個元件在哪；Stage C 尺寸與 IoU 合格，卻說不出「這條線畫錯」。
`assets/blueprint_lib.py` 產出**輪廓疊圖 + 兩類編號**來填這個洞。

**資料來源**：編號吃的是元件表——正式格式是「元件表 × 三視圖 對賬」一節的 `components/2`，
`blueprint_components/1` 只是它的單視圖 view（`CL.to_blueprint_v1()` 攤平轉換），不要平行
維護第二份。

**兩個使用時機**：

1. **Stage A 之後、Stage B 之前**（中途檢查）：元件表還是文字時先出圖。人類可回報
   「`A-3` 位置不對」「`F7` 這條曲線不對」，不必描述座標。這一步**可選**，不是每個任務都必須。
2. **Stage C**（驗收比對）：把回渲輪廓用 `extra_contours={view: [mm 輪廓]}` 餵進來，
   畫成藍虛線疊在同一份編號上——尺寸與 IoU 之外多一個人眼可讀的提示。

**兩類編號（規則）**：

- **元件 `A-1`／`A-2`…**：來自 Stage A 元件表（`blueprint_components/1`：`{id, name, view,
  bbox_mm, note, source, exclude_from_containment}`）。座標一律 mm、同 calib 的 `contour_mm`
  系（原點＝該視圖 bbox 底部中心，x 右 y 上）。**刻意凸出的構成元件**（按鍵、鏡頭凸台）
  標 `exclude_from_containment: true`——仍會量測並顯示狀態，但不列入違規。
- **特徵 `F1`…（依視圖給前綴 F/R/S/T/B）**：輪廓切成「直線／曲線／轉折／短邊／折返」，
  逐一編號；segment 與 corner **共用同一組流水號**，圖例標明類型。附長度、弦偏差、
  轉折角（含凸/凹）、外接圓半徑、外法向。
  - **主要／次要分級**：`major_min_mm` 以上（預設 3.0mm）才算主要、才標在圖上；短邊與
    折返一律次要。**次要特徵仍保留編號**，圖例列出清單，「那條 0.34mm 的短邊」照樣能引用。
    **薄型視圖（側視圖）要調小**（例 1.5）——相機凸台階差常在 1–3mm，用預設值會整批被歸為
    次要，圖上只剩外框兩條長邊。支援 `major_min_mm={'side': 1.5}` 逐視圖覆寫。
  - **`SPIKE`（折返角 ≥150°）是輪廓萃取的尖刺雜訊**，不是設計意圖的轉折——單獨一類，
    方便一眼看出「這裡的輪廓有問題」。iPhone 實測：前視圖 4 個 SPIKE、6 個 <0.6mm 短邊。
- **先擬合、後編號（切分前的前置步驟，不是選配）**：工程圖掃描出來的輪廓沿邊界是 1px 的
  階梯（實測一段圓角產生 244 個 ≥25° 小折角、1306 個 0.18–0.36mm 短邊），直接在 raw 輪廓
  上切特徵，**同一條弧會被切成十幾個 `F` 編號**——編號一多，人就沒辦法用「F7 不對」回報，
  整組特徵等於失去指認價值。所以 `segments_from_contour()` 預設先做折線擬合
  （`fit_tol_mm`，預設 0.35mm、支援逐視圖覆寫）**併掉階梯雜訊，再發編號**：實測
  1306 點 → 79 點、特徵 68 → 12 個，且擬合後不再有 0mm 的退化線段。
  `SPIKE` 與短邊只該是**擬合後的殘留訊號**（真的畫錯的地方），不是每次取樣都噴出來的常態；
  `fit_tol_mm=0.0` 可關閉（僅供測試比對，正式出圖不要關）。擬合資訊寫進 JSON：
  `views.<view>.fit = {tol_mm, min_edge_mm, n_in, n_out, removed}`。

**內縮斷言**：`assert_component_within_contour(contour_mm, comps, view, tol_mm, min_area_frac)`
回傳問題清單（不 raise）。判準是 **bbox 中心需落在輪廓內 + bbox 面積 ≥ `min_area_frac`（0.97）
落在輪廓內**——外接框套在圓角造型上時四個角本來就會落在圓角之外（幾何事實，不是錯），
不要用「四角是否在內」當唯一判準。**圓形／橢圓狀元件請用緊貼的外接框，或直接標
`exclude_from_containment`**——bbox 面積比對非矩形件天生偏低。

**輸出**：`<out>/blueprint_<view>.svg`（向量、真文字、可縮放可再編輯，底圖以 base64 內嵌）、
`<out>/blueprint_<view>.png`（點陣預覽，字級隨 `png_scale` 縮放）、`<out>/blueprint_data.json`
（特徵表＋元件表＋內縮結果＋標註統計）。**只要元件多就調小 `font_px`**（預設 10，實測 9 可讀）。
JSON 內定位：`counts.<view>.label_overlaps` 是標籤重疊數（避讓用估算字寬、非零不等於錯，
只是提示「這裡擠」）、`counts.<view>.minor_count`/`spike_count` 是次要與折返數、
`views.<view>.issues` 是內縮問題清單（空陣列＝全過）。

**已知限制**：① 特徵切分是啟發式（轉折角門檻 + 直線/圓弧貪婪擬合），不是 CAD 特徵辨識，
圓弧半徑是取樣三點的外接圓估計、切點落在交界處 ±1 個取樣點內；② **任意三點都恰可配出一個圓**，
所以 3 點以下的視窗判不出線或弧，擬合時需借第 4 點一起判（照抄時別漏掉這個退化處理）；
③ 標籤避讓用估算字寬，極端密集仍可能重疊；④ 內縮檢查只驗 bbox 位置，不驗內容正確性；
⑤ 無底圖時仍可出純向量版，但沒有疊圖可看。

## 元件表 × 三視圖 對賬（`component_lib` 比、`component_measure` 量——兩個檢查點）

**定位**：本工作流把輪廓變成量測值、「標註平面圖」一節把它畫成人可指認的圖，本節處理再
上面一層——**元件（零件）**。Stage A 拆出來的元件表（§11）與三視圖之間需要一條雙向對賬：
規劃期用圖檢查表，建模後用表校正模型。這是「兩者相乘」（見上一節）的落地機制。

**工具分工**：

| 檔 | 執行環境 | 職責 |
|---|---|---|
| `assets/component_lib.py` | 純 Python 3（stdlib；亦可由 Blender 端 import／執行） | **比**：CP1 審計、CP2 比對、核對清單 |
| `assets/component_measure.py` | Blender headless | **量**：從 `.blend` 取每個元件的實測值 |

**CP1（規劃期：元件表完成後、Stage B 動工前）**——四項檢查（A 覆蓋／B 參數／C 外觀／
D 版本史），任一有問題就 exit 1：

- `audit_coverage()`：元件宣告的視圖是否存在於 calib、框有沒有超出量測輪廓、
  **有沒有視圖完全沒被任何元件指派（盲區）**、**元件表拆解深度**（全表最深 level < 4 判不足，
  可在元件上寫 `depth_exempt` 說明豁免理由——「迭代狀態管理」規則 7）。
- `audit_params()`：每個元件的參數能不能在圖面標註或量測輪廓裡查到。來源分五級——
  `annotation`（圖面 callout）／`measured`（量測輪廓可得）／`derived`（由其他參數推算，
  須在 note 說明來源）／`estimated`（估計值——沒有圖面標註可依，含透視照推估與憑經驗填值）／
  `missing`（完全沒有）。**宣告 `annotation` 卻在 calib 的 `annotated_dims_mm` 找不到同值者
  判「虛報」**——把「我記得圖上有寫」變成可驗證的事實。參數若帶 `conflicts`（互斥候選來源）
  卻沒有 `resolved_by`，判 `conflict`、直接擋下（「迭代狀態管理」規則 3）。
- `audit_appearance()`：每個元件要嘛宣告 `appearance`（含**必填 `evidence`**），要嘛用
  `appearance_skipped` 說明不驗的理由；`flat_axis` 與 `max_extent_mm` 必須成對出現。
- `diff_tables()`（`diff` 子命令）：逐元件變更清單 ＋ **已凍結元件被改動的違規** ＋
  **本輪範圍外被改動的違規**（`--scope` 限定本輪允許修改的元件群）——版本史、凍結機制與
  一輪一元件群的實作（「迭代狀態管理」規則 1／2／4）。
- `render_checklist()`：產出 Markdown 清單，供「拿原圖 + `read_image_native`（或你的 agent 平台上等價的視覺輸入工具）」逐項核對；
  每項回答三問——**圖上看得見嗎／位置比例對嗎／有標註數字嗎**，回填後更新元件表再重跑
  audit。清單末尾附「圖譜對照（缺件）」段，要拿 `assets/anatomy/<品類>.md` 的六面清單／
  成對組件表交叉比對——**圖上有、兩邊都沒有的，才是真正的漏件**。

**CP2（建模後：框架完成、堆細節之前）**——`component_measure` 先量、`component_lib compare`
後比：逐項比對尺寸／位置／方向，容差 `pos_tol_mm`／`size_tol_mm`／`ang_tol_deg`，並對尺寸
偏差**提出建議修正的常數**（優先對應同名的 `params` 項目）。位置偏差同時給中心偏移與兩條邊
各自的偏移——非對稱元件的中心偏移不等於錯位。方向偏差需要量測端的 PCA 主軸。

**資料契約**：

- 元件表 schema `components/2`：`{id, name, level, views[], bbox_mm{view: [u0,v0,u1,v1]},
  params[{name,value,source}], objects[], axis[], note}`，外加狀態管理欄位
  （`locked`／`verified_at`／`change_note`／`appearance`／`appearance_skipped`／
  `depth_exempt`／`void`／`host`，語意見「迭代狀態管理」一節）；舊的 `blueprint_components/1`
  （單視圖單框，或 `center_mm`+`size_mm`）**可自動升級讀入**，寫出一律 v2；
  `to_blueprint_v1()` 把多視圖元件攤平成 blueprint_lib 吃得下的形狀。
  `objects[]` 支援 fnmatch 萬用字元（不分大小寫），供量測端在 `.blend` 裡找物件。
  `params[]` 每項 `{name, value, source, conflicts?, resolved_by?, resolution_note?}`——
  `conflicts` 列出與 `value` 互斥的其他候選來源，`resolved_by` 寫裁決依據（「迭代狀態管理」
  規則 3）。
- 元件表文件層（meta）：`subject`／`revision`（版本字串，改版必 bump）／`open_items[]`
  （已知未結案，不擋 CP1、但必須出現在交付說明，`audit` 會逐條印出）。
- 實測值 schema `components_measured/1`：每項 `aabb_mm`（世界軸對齊、mm）／`centroid_mm`／
  `axes`（PCA 主軸，由長到短）／`parts`（多物件時逐件 AABB）。
- 座標系同 `triview_calib` 的 `contour_mm`（原點＝該視圖 bbox 底部中心、u 右、v 上）。
  **`rear`/`back` 是鏡像視圖（u 取負）**：同一件偏 +X 的零件在 `front` 的 u 為正、在 `rear`
  為負——填表時照「圖上看到的左右」填，**不要直接抄世界 x**。對稱件看不出差異，
  非對稱件（相機平台、側鍵、連接埠）才會暴露；這個約定由自測的
  `mirror.rear.u`／`mirror.back.u` 鎖住。

**CLI**：

```
python assets/component_lib.py audit     --calib C --components K --out DIR
python assets/component_lib.py checklist --calib C --components K --out DIR
python assets/component_lib.py compare   --calib C --components K --measured M --out DIR
                                          [--pos-tol MM] [--size-tol MM] [--ang-tol DEG]
python assets/component_lib.py diff      --old A.json --new B.json --out DIR
                                          [--scope "A-1,A-2"]  # 本輪允許改的元件（「迭代狀態管理」規則 4）
python assets/component_lib.py depth     --components K [--min-level 6] [--out DIR]  # 不需 calib
python assets/component_lib.py selftest

blender --background --python assets/component_measure.py -- \
    --blend scene.blend --components K --out M [--unit-to-mm 1000]
```

> **⚠️ 兩支的 `--out` 語意不同，不要互抄**：`component_lib.py` 的 `--out` 吃**目錄**（內部
> 依 `audit`/`checklist`/`compare` 子命令各自落 `component_audit.json`/`.md` 等檔名）；
> `component_measure.py` 的 `--out` 吃**單一檔案路徑**（整份 `components_measured/1` JSON
> 寫進該檔）。把 `component_measure.py --out` 指向一個已存在的目錄，或把
> `component_lib.py --out` 指向一個檔名，兩者都不會報錯但產物位置會出乎預期。

機器上只有 Blender、沒有獨立 python 時，`component_lib` 也能用 Blender 的內建直譯器跑
（`blender --background --python assets/component_lib.py -- audit ...`，`--` 之後的參數會被剝離）。
退出碼即結論：`audit`／`compare` 有問題回 1、乾淨回 0，可直接串進場景包的 `verify_scene()`。
`compare` 產出的 `component_compare.md` 是**逐元件偏差對照表**（規劃尺寸／實測尺寸／中心偏移／
尺寸差／長軸方向／開口驗證／建議修正），不是只有統計數字——驗收時看這一份，
`.json` 給機器讀。

**強制規則**：

1. **CP1 沒過不得進 Stage B**——盲區、框超界、虛報的參數都是規劃階段的缺口，在這裡修是改
   一行文字，進了 Stage B 就是重建模。使用者要求跳過時，把未結問題原樣列進交付說明，
   不要靜默放行。
2. **`annotation` 必須被 `annotated_dims_mm` 驗證**——圖面標註是最高權威（三層優先序見下方
   「迭代狀態管理」一節），但「我記得圖上有寫」不算，要能在 calib 的標註表裡找到同值。
3. **CP2 的容差依主體尺度給**——手機類 0.5mm 起，大型物件相應放大，不要拿預設值硬套。
4. **量測端的 `objects` 樣式要夠精確**——`*` 會連停遠處的母版一起匹配，讓 AABB 橫跨兩者
   （§14 `park_master` 隔離區），優先用 `Inst_*` 之類的樣式。
5. **CP2 只認「有實測值才算過」**——元件在模型裡找不到對應物件時回報 `missing-in-model`，
   不要因為沒有量測值就當成通過。
6. **開口類元件標 `"void": true` + `"host"`，不要硬量 AABB**——USB 孔、麥克風孔、
   SIM 卡槽、喇叭網孔這些在現實中是**挖出來的洞**，模型端以布林差集建在 host 上
   （§13.10 `cut_hole()`），沒有獨立 mesh。硬把它指向 host 物件只會量到 host 的尺寸，
   產生幾毫米級的假尺寸偏差（實測 iPhone：USB 開口被誤指到連接器舌片，量到
   6.5×0.9×4.0 vs 標註 9.00×3.12，報成「尺寸差 −2.5mm」——純屬假警報）。
   標 `void` 後量測端只驗 host 存在、回報 `host_present`，比對端給 `void-ok` 狀態、
   不進缺件清單——**「量不到」與「沒建」是兩件事**，混為一談會讓開口類元件永遠卡在
   待辦清單裡。開口裡若確有可量測的實體（連接器舌片、接點），另立一項量它。
7. **凸出輪廓的構成元件用 `exclude_from_containment: true`**（側面按鍵、相機平台、鏡頭凸台
   這類刻意凸出機身輪廓的零件）：`audit_coverage()` 仍把它計入視圖覆蓋統計（它確實屬於這個
   視圖），但不列為「框超出量測輪廓」違規，超出的量記在 `views.<v>.excluded_over` 供查核。
   語意與「標註平面圖」一節 `assert_component_within_contour()` 一致，不要另立名目。

**已知限制**：① CP1 只做「幾何／資料層」的自動判定（視圖盲區、框超界、參數來源虛報），
真正的「圖上有、表中沒有」要靠核對清單 + 視覺，本層不假裝能取代那一步；② 方向偏差需要
量測端提供 PCA 主軸，只有 AABB 時略過方向項；③ 接近立方體的元件 PCA 主軸不穩定，
不要拿它做方向斷言（改用 AABB 各軸跨距）；④ 量測端只量 MESH 物件，以 EMPTY 當唯一代表
物件時會被記成 `vert_count=0` 而非 missing。

## 迭代狀態管理（`component_lib`——「改壞已驗證區」的煞車）

**定位**：前面幾節解決的是**量測能力**（怎麼知道形狀對不對）；本節解決的是**狀態管理**
（改了一輪之後，怎麼保證上一輪已經驗證過的東西沒有被順手打掉）。量測能力再強，只要
每輪都把整個場景重寫一次，正確的區塊一樣會被洗掉。七條規則全部有可執行檢查，不靠自律——
每一條都能用一個指令跑出 exit code。

**七條規則**：

| # | 規則 | 判準／可執行檢查 | 工具 |
|---|---|---|---|
| 1 | **已驗證區凍結** | 元件通過 CP2 且該鏡頭外觀已確認後，在元件表標 `locked: true` + `verified_at`（版本或鏡頭名）。動它必須先拿掉 `locked` 並寫 `change_note`；`locked` 卻被改動或刪除 → `exit 1` | `component_lib diff` |
| 2 | **單一真相源 ＋ 版本史** | 一個主體只有**一份**元件表檔（`<subject>_components.json`），禁止 `_v2`/`_v3`/`_v4` 平行檔各存一份；改版 bump meta 的 `revision`，保留上一版檔案並跑 `diff --old --new` | `component_lib diff` |
| 3 | **衝突強制停損** | 參數與圖面標註不符時寫進 `params[].conflicts`，裁決後在 `resolved_by` 寫依據；**沒裁決就 `exit 1`**，不許自動挑一個看起來合理的值繼續往下走 | `component_lib audit`（`verdict: conflict`） |
| 4 | **一輪鎖一個元件群** | 每輪修改先宣告 scope（元件 id 清單，支援 fnmatch），跑 `diff --scope`；落在 scope 外的任何新增／刪除／變更 → `exit 1`。「圖上看得出來的全部要改」拆成多輪執行，不是一輪全動 | `component_lib diff --scope` |
| 5 | **外觀也要有規格與依據** | 每個元件要嘛宣告 `appearance`（材質樣式／`flat_axis`+`max_extent_mm` 貼合平面厚度／**必填 `evidence`**），要嘛用 `appearance_skipped` 寫明不驗的理由；CP2 另外比對實測材質與貼合厚度 | `audit_appearance()` ＋ `compare()` |
| 6 | **先擬合、後編號** | 特徵切分前先做折線擬合（`fit_tol_mm` 預設 0.35mm）併掉掃描階梯；`SPIKE`／短邊是擬合後的殘留訊號，不是常態 | `blueprint_lib.segments_from_contour()` |
| 7 | **元件表拆解深度** | 兩條路線、兩個門檻：三視圖流程走 `audit`（`MIN_EXPECTED_COMPONENT_LEVEL`=4）、原創設計類走 `depth`（`MIN_EXPECTED_COMPONENT_LEVEL_ORIGINAL`=6，即 §11 Stage A item 3 的六級）→ 未達即 `exit 1`。`depth_exempt` **只認最深那個元件**（寫在淺層元件上不計入放行，會列進 `depth_exempt_ignored`），且不為了湊層級硬造零件 | `component_lib depth`（不需 calib）／`component_lib audit`（`level_histogram`）／`T.assert_component_depth()` |

**檔案位置（規則 2 的落地）**：現行版只有**一份** `<subject>_components.json`；每次改版把上一版
**移到** `<out>/history/<subject>_components.<revision>.json`（舊檔留著供 diff，但現行目錄不並列
多個平行版本）。`diff` 的 `--old` 就指封存檔、`--new` 指現行檔。看到同一目錄躺著
`_v2`/`_v3`/`_v4` 三個同級檔，就是「真相源漂移」已經發生，先合併成一份再繼續。

**優先序（規則 3 的裁決依據，由高到低）**：圖面標註（`annotation`，必須能在 calib 的
`annotated_dims_mm` 找到同值，否則判虛報）＞ 量測輪廓（`measured`）＞ 由其他參數推算
（`derived`，須在 note 說明推算過程）＞ 估計（`estimated`，含透視照推估）。**前兩者互相衝突、
且無法用第二個獨立來源（另一張細節圖／官方文案／實機照）裁決時，停下來問使用者一次**——這是
規則 3 存在的目的，不是自己選一個、也不是把兩個都記下來繼續往下做。

**凍結生命週期**：未驗證 → 通過 CP2 ＋ 外觀確認 → `locked: true` ＋ `verified_at: <revision>`；
後續要動它 → 先移除 `locked`（等於明示「這區解凍了」）＋ 寫 `change_note` → 改完重新跑 CP2
→ 通過後重新鎖定並 bump `verified_at`。**`locked` 不是宣告「永遠不能改」，是宣告「改它必須
是一個被計數、有說明的事件」**。

**交付前必附三份**（缺一即未完成驗收）：`component_audit.md`（CP1）、`component_compare.md`
（CP2）、`component_diff.md`（本輪變更與違規）；`report.json`／`SCENE_STATE` 照舊。三份都是
機器產生的，不是憑印象寫的敘述——「已驗證區有沒有被動到」由 diff 的 `locked_changed`／
`out_of_scope` 兩個計數回答，不由作者記憶回答。

**與 Stage C 的關係**：§11 Stage C 的「一輪一個方向」在本節具體化成「一輪一個元件群」——
元件群是 scope 的單位；改完一輪，只有該群的 diff 該出現變動，其餘元件應維持 `unchanged`。
`locked` 標記回答「哪些已經定稿」，Stage C 的修改輪只碰未鎖定的群。
